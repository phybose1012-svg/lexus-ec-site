# 大学入試表の復元：4セッションの実行契約

ユーザーの2026年10月9日の指示に基づき、81大学を4セッションで分担する。各セッションは1回の実行で1大学だけを丁寧に調査・作成する。入試表を外部リンクだけの案内から、読者がページ内で確認できる具体的な表に復元する。

**公開順序は「ステージングへpush → その公開表と大学公式資料をもう一度照合 → 一致を確認できた候補だけmainへpush → 本番公開確認」**。この一連の公開はユーザーが承認済みで、毎回の確認質問は不要。疑問や矛盾は推測せず、該当大学の課題として記録する。

## 担当・作業場所

- 正本台帳：`C:/---hp-seo/reports/university-admissions/manifest.json`。worker 1〜4の担当は重複しない21・20・20・20大学。
- 状態：同じ場所の `items/{slug}.json`、`workers/{worker}.json`。共有manifest全体を進捗ごとに上書きしない。
- セッション開始時に専用worktreeを最新 `origin/main` から作り、その後も再利用する。元の `C:/---hp-seo` の未コミット変更を保護する。新しい大学ごとに無制限にworktreeを作らない。
- 初期準備中は `bootstrap.json` が `preparing`。この間は最初の大学の公式資料リサーチとメモ保存を進める。公開実装は `ready` になった共通契約・レンダラーを使用する。
- 進捗・大学公式資料のスナップショット・根拠・PC/スマホのスクリーンショットは大学別のディレクトリへ保存する。他担当のファイルを編集しない。

## 一大学の手順

1. `node C:/---hp-seo/scripts/university-admissions/workflow-state.mjs next --worker N` で進行中大学を再開するか、担当の未完了大学を一つ選ぶ。共有状態の場所は常に `C:/---hp-seo/reports/university-admissions` とし、worktree別の状態を作らない。直前の本番確認から60秒未満なら、表示された残り時間が経過してから次の大学を開始する。1分の定期起動は締切ではない。調査は必要なだけ時間をかける。
2. 当該大学の医学部医学科の**2027年度**募集要項、入試案内、変更通知、試験会場案内を一次資料として確認する。PDFも内容を読み、表・脚注・訂正・発行年度を確認する。検索結果や他の予備校だけで確定しない。
3. 一般選抜前期/後期、一次/二次、共通テスト利用、地域枠などを混ぜない。以前のページに掲載されていた方式を洗い出し、公式に確認できる対象方式を網羅する。推薦等も載せる場合は独立した方式として区別する。
4. 出願登録・支払・書類提出それぞれの締切、必着/消印有効、試験日、合格発表、入学手続、科目・範囲・配点、面接/小論文の点数または評価方法、共通テスト情報I、段階選抜、試験会場の条件を照合する。値と脚注の根拠を資料名・URL・PDFページ・確認日へ結びつける。
5. 未公表の2027年度条件は、公式資料で確認した範囲と「未公表」を区別して表に記載する。2026年度の日付を1年進める、前年配点を無言で流用する、未確認を確定と書くことは禁止。十分な公式資料がない場合は根拠と再確認条件を残しdeferredにする。
6. `docs/university-admissions-data-contract.md` に沿う1大学1JSON（`frontend/src/data/universityAdmissions/{slug}.json`）を作る。本文・年度表示・title・description・目次・出典は共通レンダラーで揃える。制作過程の報告文や内部JSONを読者の画面に出さない。
7. セルごとに `reconciliation-{slug}.json` を保存し、掲載値、公式資料の該当箇所・引用/要約・ページ、一致/未公表の判断を記録する。原稿が完成しただけでは公式再照合完了にならない。
8. 意味テストとページ検証・ビルド・PC/スマホの目視を行う。自動の語句一致は入試条件の意味の検証を代替しない。

## ステージングから本番への反映

1. 候補JSONのSHA256と当該大学だけの差分を確定する。共通レンダラーの変更はroot担当であり各セッションで書き換えない。
2. 公開用の共有lockを取得する。取得できなければ候補やリサーチを保存して終了し、次回同じ大学を再開する。ロックを勝手な時間切れで解除しない。
3. 最新 `origin/staging` をfetchし、担当のstaging用worktreeへ**当該大学の候補ファイルだけ**を適用する。他担当のステージング作業を保持する。ステージング設定でビルドし、通常pushする。
4. Cloudflare Pagesの当該commitのcheck-runs成功を待ち、`https://staging.lexus-ec.pages.dev/information-{slug}/` で取得する。表・年度・方式・脚注・出典リンクを確認し、**実際にステージングに表示された全セルを公式資料と改めて照合**する。PC/スマホ表示を確認し証拠を保存する。
5. 不一致があればステージングで修正し、同じ検証を繰り返す。合格した候補JSONのhashを固定する。公開GET・PC/スマホ画像・全セルの公式比較を含む更新JSONを渡して、`node C:/---hp-seo/scripts/university-admissions/workflow-state.mjs update --worker N --slug SLUG --file UPDATE.json` で `staging-verified` を記録する。この検証が成功した大学だけ次のmain反映へ進む。確認後にJSONが変われば公式再照合をやり直す。
6. 最新 `origin/main` をfetchし、本番用worktreeへ同じhashの**当該大学ファイルだけ**を適用する。stagingブランチ全体をmainへmergeしない。過去問ライブラリーの公開制御、既存10月表示、他担当の変更を維持する。
7. `CF_PAGES_BRANCH=main` で必要な検証と本番ビルドを行い、通常pushする。force pushは禁止。最新mainへの統合で候補以外の差分がある場合は原因を確認する。
8. Cloudflare Pagesの公開成功と `https://lexus-ec.com/information-{slug}/` の表、同一候補、PC/スマホ表示を確認する。Git push成功だけで完了としない。
9. stateのpublishedを証拠付きで記録する。staging/main commit、候補hash、公式比較ファイル、公開GET・画像を台帳に残す。公開lockを所有tokenで解放する。途中で失敗した場合、証拠と未完了の段階を残す。

## 自動継続・終了

各セッションのheartbeatは、次の大学へ進むための起動手段とする。一大学の実行中は、調査・原稿・検証・staging・公式再照合・main確認を可能な限り同じ実行で連続して進める。状態ファイルの確認だけで終了して毎分同じ確認を繰り返さない。作業中の大学を重複開始せず、公開確認完了時刻から60秒後を `nextEligibleAt` として次の大学を開始する。スケジューラの遅延やPC停止時に厳密な秒数を保証しない。

**2026年10月9日の追加指示：完了・停滞時には自動起動を止め、エンドレスなプロンプト送信を禁止する。** 起動時と終了時は [自動継続の停止判定](university-admissions-continuation.md) と `continuation-guard.mjs` の判定を使う。全担当対象がpublished/deferredだけなら停止する。未解決の共通障害や権限・外部条件で進めない場合も、その根拠と再開条件を残して自分のautomationを `PAUSED` にする。成果の実内容が変わらない起動が3回続く、同じエラーが2回続く、または同じ大学の起動上限に達した場合も停止する。更新日時・巡回ログ・同じJSONの保存・レポートの再生成は成果に数えない。停止後はユーザーまたはrootの明示的な再開と原因の解消が必要で、無期限の自動再試行を設定しない。

一つの大学が完了したら短く大学名・対象年度・staging/main URL・確認記録・残る未公表項目を報告し、報告HTMLを再生成する。lock待ちの再試行も上限を設ける。割り当てが全てpublishedなら自分のheartbeatを停止し完了件数を報告する。deferredが残る場合は完了とは呼ばず、公式資料の公開待ちと再確認条件を報告し、無益な毎分の再調査を止める。

本タスクのユーザーは4セッションへの自動プロンプト送信を承認している。他の既存セッションや無関係のautomationは変更しない。
