# 大学別入試記事の校閲・整形フロー

制定日：2026年10月10日。筑波大学ページでユーザーが確認した編集方針を、大学別入試記事の共通基準とする。

復元された情報を公式資料で校閲し、受験生が募集人数・日程・科目・配点・条件を読み取りやすい記事にする。作業単位は「1大学・1入学年度」。工程と編集規則を共通にし、各大学の選抜方式と条件に合わせて構成を調整する。

## 着手条件

- 復元担当が確定した候補、公式資料、対象ページ、候補hash、staging commit、既存の検証結果を受け取る。復元途中の候補は確定版を待つ。復元完了と編集完了を別に記録する。
- [大学別確認票](templates/university-admissions-editorial-review.md)を複製し、`reports/university-admissions/{slug}/editorial/` に証拠とともに保存する。担当を分ける場合も、同じ候補と確認票を引き継ぐ。
- 復元台帳、担当割当、root監査、公開ロックは保持する。[公開手順](university-admissions-workflow.md)の必須ゲートと、稼働中のroot承認設定に従う。表示変更の証拠を旧形式の検証結果へ付け替えない。
- 本番反映の権限は、現在の人間の指示・適用中の公開契約で確認する。今回の筑波大学の指示を、他大学への一括公開許可として扱わない。

## 記事の標準構成

| 順序 | 要素 | 掲載内容 |
|---|---|---|
| 1 | タイトル | `{大学名} 医学部{入学年度}年度入試情報`。医学科・医学類など正式名称は本文で明確にする。 |
| 2 | 導入 | 日程、会場、科目、時間、配点、出題範囲等を選抜方式別にまとめた記事であることと、出願前の公式要項確認を短く案内する。掲載していない項目を掲載済みと書かない。 |
| 3 | この記事の要点 | 原則3項目。主要方式の募集人数・日程、科目・配点の特徴、推薦等の条件から、受験生の判断に役立つ具体的な事実を選ぶ。 |
| 4 | 入試方式・募集人数・主要日程 | `入試方式／募集人数／出願／試験日` の一覧。方式名から詳細へ移動できるようにする。 |
| 5 | 方式別詳細 | `出願・試験・手続の日程 → 出願資格・推薦条件 → 試験科目・配点 → 試験会場・受験票 → 併願・出願時の注意` の順。必要な項目だけ置く。 |
| 6 | 公開予定・固有制度 | 未公表資料の公開予定を短く案内する。入学後の医学科への移行、地域枠の勤務条件など、説明が必要な制度は独立した節にする。 |
| 7 | 大学基本情報 | 最新の公式所在地・アクセス・公表統計。統計の年度、対象、総人数を表に明記する。学納金を載せる場合も公式年度を確認する。 |
| 8 | 情報ソース | 入試・固有制度・基本情報それぞれの末尾に、小さな「情報ソースはこちら」。資料一覧は折りたたみにまとめる。 |

要点に確認日、調査完了の報告、注意事項の羅列を入れない。確認日は情報ソース等へ置く。冒頭の短い要約から詳細へ進める構成を保ち、表を説明し直す段落は作らない。

## 固定の8工程

| 工程 | 作業 | 次へ進む条件・記録 |
|---|---|---|
| 1. 確定版受領 | 年度・大学・学部学科・方式と対象範囲を確認し、候補hashと入力commitを固定する。 | 確認票に入力一覧と対象範囲がある。 |
| 2. 正確さの校閲 | 全項目を公式原典と照合し、基本情報も最新公表資料で調べる。不一致は修正して再照合する。 | 原典URL・ページ/節・判断・確認日時を全項目に記録。未公表の根拠も残す。 |
| 3. 構成の割当 | 標準構成へ情報を割り当て、一覧・詳細・制度説明・基本情報の掲載場所を決める。 | 各事実に表示先がある。省く重複・編集メモとその理由を記録する。 |
| 4. 整形 | 数値は表、時系列は日程表、資格条件は短い段落や箇条書きにする。出典を表の外へ移す。 | 下記の編集規則を満たし、正本との対応・出典ID・未公表状態を保持している。 |
| 5. 文章・画面確認 | 重複と作業メモを読み直す。機械検証・必要なビルド・PC/390px/320pxで全表を確認する。 | 必須条件が欠落せず、人数・日付・配点合計が一致。目次・情報ソース・狭い画面での表示が使える。 |
| 6. staging確認 | 公開ロックを取り、当該大学の変更だけを最新stagingへ通常push。該当commitのCloudflare成功後に実ページを新たに取得する。 | 全表示項目を候補・原典へ再照合し、PC/390px/320px画像と実結果を保存する。 |
| 7. main反映 | 適用中の承認条件を満たし、承認済み差分を最新mainへ選択移植する。本番用検証・ビルド後に通常pushする。 | 値と表示が検証済み版と同一。staging全体のmerge、他大学の候補の混入、force pushをしない。 |
| 8. 本番確認 | 該当main commitのCloudflare成功後に実ページを新たに取得し、全表示項目・PC/スマホ・目次・情報ソースを確認する。 | 本番commit・URL・実結果・画像を記録し、所有する公開ロックを解除して編集完了とする。既存の待機条件も守る。 |

候補や表示を変えた場合は、影響する校閲・画面確認・staging確認をやり直す。mainとの統合でも表示が変わっていないことを確かめる。確認票を埋めただけでは合格にしない。

## 必須の編集規則

### 表を短くし、条件を保持する

- セルは事実を先に、固有の条件を次に示す。日程・資格・配点・会場を一つの長文に詰めない。
- 配点は教科・試験を行に、共通テスト・個別試験等を列にした数値表を基本にする。科目選択、換算、第1段階選抜などは近くに短く残す。
- 「課さない」「未公表」「要確認」「予定」を区別する。記号だけで意味を曖昧にしない。
- Web登録、検定料、書類提出の締切を統合しない。時刻、必着/消印有効、郵送/持参を保持する。
- AND条件は「すべて必要」、OR条件は「いずれか」を明示する。例外、免除、経過措置を短縮のために削らない。
- 共通枠・複数募集月の合計人数には対象範囲を表示し、方式別の独立した人数として足し合わせない。配点・会場・資格も方式ごとに原典で確認する。

### 情報ソースを控えめに置く

- 表のセル、資格条件、要点の中に出典番号、出典を示す括弧書き、資料名、PDFページ番号、外部資料リンクを入れない。条件そのものの括弧書きは保持する。
- 表の下や節の末尾に小さく「情報ソースはこちら」を置き、対応する公式資料一覧を開けるようにする。目次・方式への内部リンクは使ってよい。
- 題名、URL、年度、参照ページ、確認日は資料一覧と内部の校閲記録に保存する。見た目から出典を外しても根拠を消さない。
- 折りたたみに入れるのは情報ソースとその補足。資格、締切、配点、例外、未公表状態は本文で見せる。

### 重複と作業メモを除く

- 表の人数・日付・点数・合計を、その直下で文章として繰り返さない。表にない換算規則、例外、義務などだけを残す。
- 「転用しない」「推測していない」「本表の掲載対象」「原典の記載を確認した」など、編集指示や作業報告は公開本文から外して内部記録へ移す。
- 未公表の範囲は具体的に示し、必要なら「募集要項の公開後に更新します」と受験生へ案内する。取得失敗や矛盾を「未公表」に言い換えない。
- 原典間の日付・曜日の矛盾など、受験上の行動に影響する不一致は根拠付きで保留し、断定して公開しない。単なる作業メモと受験上の注意を区別する。
- 固有制度の見出しは読者が得られる情報を示す。手順は順に説明し、希望者全員の進学・合格を保証する表現を避ける。

### 基本情報を最新の公表資料へ更新する

- 本部と医学科の所在地・連絡先を区別する。アクセスは公式の経路、所要時間、最寄り駅・バス停を確認する。
- 男女比・現浪比等は医学科の最新公表年度と対象をそろえ、「志願者」「合格者」「入学者」を混ぜない。
- 表題に `対象年度／対象集団／総人数`、列に `区分／人数／割合` を示す。割合は同じ母数から計算し、原典のラベルと人数を再照合する。
- 医学科の統計が未公表なら大学全体の統計で代用しない。最新公表年度の確認日、掲載できない理由を内部記録に残す。

## 大学ごとの調整と実装

方式数、教科、配点列、試験段階、地域枠、学納金、固有制度は大学の公式資料に合わせる。不要な節や空の表は作らない。筑波大学の人数・科目・方式を他大学にコピーしない。

筑波大学の実装は `frontend/src/lib/tsukubaAdmissionsReadable.ts`、文言は `frontend/src/data/tsukubaReaderCopy.json`、検証は `frontend/scripts/verify-tsukuba-readable.mjs` にある。現在の検証は筑波大学専用であり、他大学の合格証拠に使わない。他大学でも元の全項目と表示先の対応を検証する。

共通レンダラーを拡張する場合は、大学固有の条件を表示設定として分け、未対応大学を一括切り替えない。対応済み大学と代表的な方式の表示・条件保持を検証してから採用する。この文書の制定だけで全大学のページを変更したことにはならない。

## 完了の定義

公式との一致、条件保持、読みやすい表示、重複・作業メモの除去、控えめな情報ソース、stagingと本番の実表示確認がそろって「編集完了」とする。未公表・不一致・取得障害は、対象項目と根拠・再確認条件を記録して区別する。次回もこのフローと大学別確認票から再開する。
